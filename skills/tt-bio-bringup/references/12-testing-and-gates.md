# 12. Testing and gates

This document decides what your port's test suite must assert, how to write a gate that cannot pass
vacuously, and what the repo's gate script should look like. A gate is a claim that something is
true, and almost every gate bug in this codebase's history was not a wrong threshold but a gate
quietly not testing the thing its name says. Assume that of yours until you have watched it go red.

Read this when you are adding tests for a newly ported component, wiring a model into the release
gate, debugging a gate that reads green while the model is visibly wrong, or triaging a perf alarm.

## 1. The four layers

| Layer | Asserts | Against | Home |
|---|---|---|---|
| Unit parity | each ported component matches the CPU golden | fixed input, per module | `tests/test_<model>_*.py`, loading the reference from `scripts/<model>_port/` |
| End-to-end parity | the whole device path matches the reference path | committed fixture, fixed seed | `scripts/full_parity_gate.py` leg |
| Task metric | the artifact the user receives is scientifically right | small held-out set + ground truth | `scripts/release_gate.py` arm |
| Perf regression | warm throughput has not moved | fixed small input, committed baseline | `scripts/perf_regression.py` entry |

- **Unit parity** scores a number at the component's own boundary. The bar is the measured bf16
  self-envelope from `02-parity-and-correctness.md` §3.4, not a fixed constant; PCC ≥ 0.98 per module is
  a plausibility floor, so a number under it is definitely wrong and a number over it is not
  automatically right. Maxdiff exactly 0 is far stronger and available wherever the device path is
  meant to be bit-exact (`04-shapes-tiles-and-bucketing.md` §6 covers which ops stay bit-exact under padding). Keep a
  random-weight reference module beside the test so it runs without a checkpoint download.
- **End-to-end parity** asserts the composition, which no unit test does. The classic escape is a
  component that is bit-exact and whose output is then dropped or fed to the wrong consumer. Score
  the tensor the next stage actually reads.
- **Task metric** asserts the science against real ground truth, at a floor near 2x the measured
  value: it catches a gross failure, it does not track drift. Self-consistency is not a task metric,
  a seed-vs-seed RMSD passes while the fold is wrong. A design model with no ground truth is gated
  on designability (refold the designed sequence, check the shape reproduces) or delivered-artifact
  geometry **over the designed residues only**: averaging designed against copied residues passes
  by dilution.
- **Perf regression** measures warm steady-state on a tiny input with model load and first-kernel
  compile excluded. It catches dispatch and kernel regressions, not accuracy. No arm does both.

## 2. Anti-patterns: gates that pass vacuously

### 2.1 The check passes when the op it names never ran

On a residual or near-identity stack, an absolute correlation gate named after one op is satisfied
by the skip connection, not by the op. Measured on a hoisted LayerNorm inside a 24-block DiT: the
correct implementation scored 0.99899, applying the norm twice scored 0.99999 (LayerNorm is
near-idempotent), scoring the pre-norm activation with the norm skipped entirely scored 0.99503. A
`> 0.98` gate passes all three.

- **Detect:** score the deliberately broken controls first (op skipped, op applied twice, wrong
  tensor scored). A gate that cannot fail on a control obviously lacking the op is not testing what
  its name claims.
- **Fix:** assert the path fired (a counter in the kernel wrapper, a hook recording the call, a
  log-line assertion) *and then* assert the number.
- **Guard:** commit the negative control as a test asserting the gate FAILS on the broken variant.
- **Sibling signature:** a leg where the measured difference and the noise envelope both round to ~0
  with a clean PASS is usually both sides generated by the same code path, with no external
  reference. `num=5e-15 env=5e-15 ratio=0.00` is a bug report on the gate, not a result.

### 2.2 The check verifies a file exists, not that its content is right

A gate guarding on `os.path.exists(golden_path)` while the test body reads specific keys inverts its
own failure mode. A partial capture (7 of 17 keys) produced 11 `KeyError`s that read exactly like a
code regression in whatever branch was checked out; the suite went 11 failed to 0 failed with zero
change to the model code. Fix: grep what the test actually reads and assert on those keys or on a
content hash. Where a fixture is legitimately per-host, skip with a reason naming the script that
regenerates the key, never index `dict[key]` directly. Guard: a `--check` preflight that validates
every leg's fixture, target id and config in seconds without opening a card.

### 2.3 The check re-reads a committed verdict instead of recomputing the value

An annotation like `[reproduces committed]` that compares the PASS/FAIL bucket does not re-diff the
metric: a number can drift and still read clean while it stays on the same side of the bar. Diff the
value, at a precision that shows its sign (a bound of `-4.67e-5` rendered at four decimals as
`-0.0000` has been read as a zero crossing). Related: an `EXEMPT`/`SKIP` reason string goes stale
while the exemption stays green, so grep your model's slug in every exempt list before merge and
re-verify the reason in the same commit.

### 2.4 The check scores the installed package while you edit a checkout

Python puts the script's own directory on `sys.path[0]`. A leg under `scripts/` doing `import tt_bio`
in-process resolves to whatever is `pip install -e`'d, not the tree the gate lives in. Install ==
checkout hides the bug; a newer checkout fails loudly; an **older** checkout passes while measuring
the wrong code, with no signal at all.

Fix: run legs as subprocesses with `PYTHONPATH=<repo root>` explicit, and print the resolved
`tt_bio.__file__` and version in the gate banner. Same class on the perf axis: `importlib.metadata.version("ttnn")`
is a git-describe string frozen at install time for an editable install, and drifts as soon as you
commit again, so a row measured on a literally identical tree reported incomparable for two weeks.
Key comparability on the commit the dependency was built from, proven with `git diff <pinned-commit>`.

### 2.5 The gate's interpreter differs from the runtime it certifies

A release gate launched with the system `python3` gates whatever `ttnn` is on that interpreter's
path, not what `pyproject.toml` pins. One such run had two legs read high enough to fail a release
as numerics drift on a difference that was never code. Fix: a preflight refusing to start unless
`importlib.metadata.version("ttnn")` matches the pin, and printing it; launch through the release venv's
`sys.executable` with `PYTHONPATH` at the tag tree, so your code is under test while the dependency
comes from the pinned venv. A bare `python3` in a release runbook is a red flag.

### 2.6 Inverted shell exit-status logic

`grep -L PATTERN FILE && echo OK` is backwards: with a single file argument GNU grep's exit status
still reports whether a line was selected, so the `&&` fires exactly when the bad string IS present.
The check can never be satisfied by a correct file, and repeatedly "fixing" the target looks like a
flaky test rather than a backwards one. Correct form for "this string must be absent":

```sh
! grep -q "PATTERN" FILE && echo OK
```

Same family: `python3 gate.py | tail -8; echo RC=$?` reads `tail`'s status, so a red gate prints
`RC=0`. Redirect full output to a file and inspect the file, or read `${PIPESTATUS[0]}` immediately
after the pipeline. An interactive shell may also alias `grep` to another implementation with
different exit semantics, so verify any gate condition with `command grep` or a fresh `bash -c`.

**The rule covering all three: test the gate by breaking the thing it guards.** Revert the fix or
inject the regression, confirm it goes red. A gate never observed failing is not a gate.

### 2.7 A hardcoded absolute path or a duplicate resolver

A leg hardcoding `~/.cache/<something>/model.ckpt` instead of calling the repo's weights resolver is
green only on the machine it was written on. One died with `FileNotFoundError` after paying for
featurization, on a host where the checkpoint sat under a different resolved path the whole time,
and took an already-merged sibling leg down with it. Call the single resolver, never re-derive path
logic in a harness. Once a gate file has three or more per-model branches, replace the if/elif chain
with a table (`DELEGATED_KINDS = {slug: handler}`), one row per model.

### 2.8 Coverage split across two gate files

"Does model X have a leg" is the wrong audit question: a model can be covered in the bit-exact
parity gate and absent from the end-to-end release gate, so a single-file grep reads as uncovered
when it is covered differently. Worse in the other direction, one model had a bit-exact featurizer
leg, a perf leg and a UX leg, and nothing scoring the structure that came out. Ask instead: **which
end of the pipeline does each leg score** (input featurization, an intermediate tensor, a
wall-clock, or the delivered artifact), and write that mapping down. Coverage that stops before the
artifact is the shape that ships dropped outputs.

## 3. Perf gates specifically

- **Single-shot legs false-alarm on their own noise.** A leg with no warm loop (one-shot design or
  affinity call) measures ±20-30% run-to-run, so a 15% threshold alarms forever on nothing. Run the
  whole end-to-end invocation `SINGLE_SHOT_REPEAT = 3` times back-to-back and gate on a statistic.
  Which statistic is decided two bullets down: the median while the box is quiet, the **min** the
  moment host contention is in play, because contention only ever slows a rep.
- **Warm legs: warm up, then median.** `WARMUP = 2` folds absorb first-kernel compile and are
  excluded; `REPEAT = 5` timed folds give the gated median.
- **Host contention is one-sided noise.** It can only slow a rep, so a median of 3 still reports a
  contended value when 2 of 3 reps are contended. Three runs of identical code once read -29%, -46%
  and -24% purely as a function of host load, while the run on a quiet box had a rep *faster* than
  baseline. For one-sided noise the robust statistic is the **min** rep: a tree that produced a rep
  faster than baseline did not regress. Also refuse to start above a load ceiling (1.5x `nproc`).
- **Record the conditions, not just the number.** A baseline entry must be self-describing:

```json
"yourmodel": {"unit": "structures/s", "direction": "higher", "value": 1.25, "latency_ms": 800.0,
  "input": "trpcage (20 aa, single-seq)", "sampling_steps": 10, "diffusion_samples": 1,
  "recycling_steps": 1, "warmup": 2, "repeat": 5, "hardware": "blackhole", "card_type": "p150a",
  "tt_bio_version": "0.7.1", "date": "2026-01-01"}
```

- **Key baselines by card type, and by machine where machines differ.** A p300c number judged
  against a p150a run reads as a false 20-34% regression that is just the part; two machines with
  the same card type have read 30-36% apart on the same models. A detected card type with no
  recorded baseline must FAIL loudly, not skip.
- **A baseline in a file is historical.** Other levers land and move the model's runtime without
  anyone re-recording, so scoring a change as `committed_baseline - new_measurement` credits it with
  all drift since: one lever measured a 1.318 s win against a published cell whose true same-run
  value was 0.526 s, a 2.5x over-credit. Score against a same-run control arm on the same card in
  the same process, and treat the committed number as the thing to *update*. Re-measure the baseline
  whenever hardware, driver or the dependency stack changes.
- **Before bisecting a perf alarm, run an endpoint A/B:** baseline commit vs current HEAD,
  interleaved reps, same host and cache. If the endpoints match, the recorded baseline was the
  outlier. Reseed honestly and stop.

## 4. Every escaped bug becomes a permanent gate arm

The same change that fixes a bug which reached a user adds a gate arm for it, in the DEFAULT arm
set, and **that arm must be demonstrated FAILING on the pre-fix commit** or it is theatre. The arm
is the minimal reproduction of that specific mechanism, not a broad new test.

Worked example: a user on a part with ~22% less per-core L1 than the development part hit a static
circular-buffer clash, because L1 budgets calibrated on one part were applied unscaled to any grid
above a core-count threshold. The gate structurally could not fail: every part in the lab had at
least the calibration L1. The arm that closed it is a table-driven per-part L1-budget assertion (one
row per part class, each a measured figure with provenance) plus a test-only per-core-L1 override
env so an available part can behave like a smaller-L1 one. **A part-specific resource figure
entering the code gets a gate row in the same commit.**

## 5. Coverage blind spots

- **Parts and dependencies you do not own.** The gate only runs on what is in the room. If a
  constant is calibrated against a measured hardware property, simulate the missing value behind a
  test-only override instead of skipping. "We do not have that part" is not a reason to skip.
- **A hardcoded model list misses the model added next,** and fails *silently* (the model is simply
  absent from output). Derive it from a single source of truth:

```python
tuples  = {n: getattr(main, n) for n in dir(main) if n.endswith("_MODELS")}
shipped = set().union(*tuples.values())
uncovered = shipped - set(SPECS) - set(SPECS_EXEMPT)
if uncovered:
    raise SystemExit(f"no perf coverage for {sorted(uncovered)}; add SPECS or a SPECS_EXEMPT reason")
```

  Discover the tuples, do not name them: a version written against the three that existed at the
  time went blind when a new CLI verb brought its own tuple, and the model it was built to protect
  could have shipped uncovered.
- **A fixture too small or too soft cannot express the failure.** A chimeric two-domain fixture with
  no real inter-domain interface saturates all-atom RMSD at ~8 Å for *any* non-bit-exact change:
  four unrelated changes all landed in the same 7.7-9.0 Å band, while per-domain superposition
  showed every arm kept both domains at 0.73-1.45 Å and differed only by a hinge rotation. A number
  invariant to which change produced it is not measuring the change; the monomeric control on the
  same fixture family moved 0.28-0.33 Å for the identical changes.
- **A probe with no positive control proves nothing.** A memory-taint probe reported "clean" because
  the plant landed at one address while the op's output buffer sat elsewhere. Prove the probe fires
  on a planted defect in the same run.

## 6. Determinism and flakiness policy

Do not loosen a tolerance to make a test pass. The procedure:

1. **Run the unchanged code N ≥ 3 times on the same host, card, tree and process shape.** That is
   the noise floor; any diff below it is not attributable to your change. This one control retires
   most "flaky test" claims, in both directions.
2. **Same input, same seed, different bits on the same card is a hardware or allocation problem.**
   One card was found silently miscomputing some matmuls at a low, location-keyed, data-independent
   rate: transfers were bit-exact over 4x256 MB, `concat` and `layer_norm` stable at every size, and
   a single 512→256 matmul differed on 15/15 repeats in fp32 and 2/31 in bf16. The originally
   observed "512 aa only" framing was an artifact of one sample per size; a matched card elsewhere
   was 15/15 clean on the same commit. Quarantine such a card from every bit-exact leg at every
   size, and never let an "any free card" scheduler place a bit-exact check.
3. **Size-conditioned nondeterminism is a code path switching on, not float noise.** One model was
   bit-exact at 128 aa across three folds and diverged up to 3.17 Å at 384 aa with a fixed seed.
   Before calling any A-vs-B hash comparison a signal, run the A-vs-A floor control at the same size
   in a fresh process; there, the reported signal sat entirely inside the floor.
4. **Environment gaps are not regressions.** A leg failing only for models needing an external MSA
   service, or only with a reference-repo env var unset, is an environment problem: fix it, cache
   the input so the gate runs offline, re-run that leg.

## 7. The gate script itself

One script, arms selectable by name, all arms by default.

```
scripts/release_gate.py
  __doc__        per arm: what it folds, what it asserts, why the floor is where it is, and which
                 escaped bug it exists to catch. This docstring is the spec.
  MODELS         {slug: (target, ground_truth, rmsd_floor, tm_floor)}
  DEFAULT_ARMS   non-fold arms (design, capacity, l1-budget, determinism, ...)
  preflight()    interpreter + pinned dep version, card grant, host load, fixtures. Refuses with
                 exit 2, printing every problem at once.
  run_<arm>()    returns {"model", "gate": bool, "error", "seconds", ...metrics}
  main()         run selected arms, one table per arm, AND the verdicts, exit
```

```
##############################################################################
RELEASE GATE: 7ROA (117 aa), seed 48, card p150a, ttnn 0.68.0, tt_bio <resolved path>
##############################################################################
model            RMSD (A)      TM           floor     wall  result
inherited            1.55   0.913   <=3.0A >=0.80    52.1s  PASS
yourmodel            7.42   0.412   <=3.0A >=0.80    61.7s  FAIL
##############################################################################
GATE FAIL: yourmodel missed the ground-truth floor (see above)
```

Exit `0` every selected arm passed; `1` an arm failed its assertion, the code under test is suspect;
`2` preflight refused (wrong interpreter, wrong dependency version, missing fixture, host
overloaded, no card grant) and nothing was measured. Keep 1 and 2 distinct so an automated caller
can tell a bad tree from a bad host.

- Every arm folds its `gate: bool` into one `all_pass`. An arm that appends a row and returns
  silently makes a refused arm look identical to one that was never requested.
- Print resolved code path, dependency version, card type and seed in the banner. A gate output that
  does not say what it measured cannot be audited later.
- Dry-run any new or significantly changed gate script end-to-end on a real release candidate before
  trusting it as gate-of-record. One release cost a full day of thrash with zero model-numerics
  problems: every failure was in the never-exercised harness.
- "Gate green" as prose is not evidence. Paste the arm-by-arm table with the numbers.

## 8. Pre-merge checklist for any change to the port

- [ ] Unit parity passes at the bar each touched component claims (PCC ≥ 0.98, or maxdiff 0 where
      the path is meant to be bit-exact).
- [ ] End-to-end parity leg re-run, with the *value* diffed against the number your docs quote, not
      just the verdict.
- [ ] Task-metric arm re-run on hardware known good for the check class; bit-exact and hash-equality
      checks pinned away from any quarantined card.
- [ ] Perf gate re-run; a regression endpoint-A/B'd before it is called one; an improvement scored
      against a same-run control arm, never against a published number.
- [ ] If this fixes a bug that reached a user: a new gate arm exists, sits in the default arm set,
      and has been demonstrated FAILING on the pre-fix commit.
- [ ] If this adds a model, a CLI verb, or a part-specific constant: grep every hardcoded model
      list, `*_EXEMPT` map, size-ladder list and registry dict, add the entry in this commit, and
      re-verify the reason text on any exemption you touch.
- [ ] New or edited gate legs run as subprocesses with explicit `PYTHONPATH`, resolve checkpoints
      via the repo's resolver, and have been observed going red on a broken variant.
- [ ] Every shell condition in a gate or CI step verified with `command grep` / `bash -c`, exit
      status read from the producer and not from a pipe.
